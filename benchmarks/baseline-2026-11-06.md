# Initial performance baseline

This is a historical exploratory run from the custom runtime harness. Runtime benchmarks have since moved to BenchmarkDotNet.
The raw data remains unchanged; it must not be presented as BenchmarkDotNet output.

The first run puts additional DSL model-construction time below the proposed 10 ms budget at 100 declared resources.
Build times need further work and a cleaner consumer comparison. These are local observations, not release guarantees.

## Environment and method

Measured November 6, 2026 on an Apple M2 with 8 logical CPUs, macOS arm64, .NET SDK 10.0.400, and Aspire 13.6.4.
Applications targeted .NET 10 and ran with the installed .NET 10.0.11 runtime.
Packages and build outputs were warm. OS caches were not cleared.

The [raw report](results/2026-11-06-macos-arm64.json) records environment details and samples.
It identifies commit `d7cb016` plus the uncommitted benchmark files present during the run.
The [benchmark methodology](README.md) defines each measurement and its limits.

Each resource count has 45 warm construction samples per implementation, from 3 processes with 3 warmups and 15 measurements each.
Fresh-process and build measurements have 5 samples each.
All model fingerprints matched across C#, native F#, and the DSL.

## Model construction

All times below are medians in milliseconds. Construction includes creation of the native Aspire builder and resource registration.

| Declared resources | Native C# | Native F# | DSL | DSL minus native F# |
| --- | ---: | ---: | ---: | ---: |
| 5 | 71.67 | 68.96 | 69.74 | +0.78 |
| 25 | 73.82 | 73.97 | 72.92 | -1.05 |
| 100 | 83.22 | 84.55 | 87.40 | +2.86 |

At 100 resources, the DSL median was 3.4% higher than native F#.
The construction p95 values were 97.07 ms for native F# and 96.42 ms for the DSL.
These overlapping distributions do not establish a consistent tail-latency difference.
The negative median difference at 25 resources should not be interpreted as a DSL optimization.

At 100 resources, median construction allocations on the measuring thread were 2,464,680 bytes for native F# and 2,544,856 bytes for the DSL.
The difference was 80,176 bytes, approximately 78 KiB or 3.3%.
These counters exclude allocations on other threads and do not measure retained memory.

Native host `Build()` medians at 100 resources were 1.87 ms for native F# and 1.93 ms for the DSL.
The median fresh-process total was 305.22 ms for native F# and 322.75 ms for the DSL.
That process interval includes model reporting and disposal; it does not measure dashboard or application readiness.

## Source-project builds

All values are medians in milliseconds, including the `dotnet build` process.

| Build scenario | Native C# | Native F# | DSL |
| --- | ---: | ---: | ---: |
| No source changes | 982 | 2,290 | 1,253 |
| AppHost source edit | 1,272 | 2,540 | 3,180 |
| Rebuild source dependency graph | 1,744 | 3,298 | 7,281 |

The DSL AppHost-edit median was 25.2% higher than the native F# median in this setup, exceeding the proposed 10% target.
The DSL graph also builds the core and Redis libraries, which the native graph does not contain.
These results cannot isolate DSL syntax costs from project-graph and tooling costs.
The source uses loop-based declarations, so the build measurements do not test inference across hundreds of separate resource expressions.

A follow-up no-change check warmed each project independently before checking DLL timestamps.
The DSL and native C# rewrote no DLLs. Native F# rewrote its AppHost DLL.
The [output check](results/2026-11-06-no-change-outputs.json) records these observations.

An MSBuild diagnostic build reported that native F# `CoreCompile` ran because generated `_AppHost.ProjectMetadata.g.fs` was newer than the intermediate assembly.
That input comes from the FSharp.Aspire.Hosting.AppHost package's metadata-generation target.
The core DSL library excludes those package build assets and uses project paths.
Do not treat the native F# result as a clean no-op baseline or attribute its extra time to F# alone.
The benchmark runner now records rewritten DLLs for future no-change samples automatically.

## Next measurements

1. Add published-package consumers to separate library source builds from user AppHost builds.
2. Compare native F# with and without metadata-generation build assets while preserving the same runtime APIs and project-path behavior.
3. Measure compiler inference with separately written resource expressions at increasing topology sizes.
4. Measure dashboard and application readiness as distinct events, with restore and image pulls reported separately.
5. Repeat on a quiet machine before enforcing build budgets in CI.

These results do not justify runtime optimization yet. Build and tooling isolation should come first.
