# Aspire startup comparison

The comparison uses the existing Redis, API, and frontend sample. The same AppHost executable selects either the AspiringFarmer DSL or the direct F# Aspire declarations. Both HTTP services use ports allocated by Aspire.

Run from the repository root with OrbStack running and the `redis:8.6` image cached.

```sh
dotnet build prototypes/NativeAspire -c Debug
python3 benchmarks/startup.py --pairs 3
```

The runner randomizes implementation order within each pair with seed 42. Each trial starts a new CLI session and uses the prebuilt Debug AppHost. The runner verifies the executable path in the Aspire log. Aspire runs its normal service build and launch workflow for the API and frontend.

Both times start immediately before the runner launches `dotnet run --no-build`. Dashboard readiness is the first successful HTTP response from the local dashboard. Resource readiness is the first observation of all three Aspire ready messages. The runner polls at 50 ms intervals and records when it sees each message. After each trial, it stops the session and waits for that trial's Redis container to stop.

The trials ran on macOS arm64 with .NET SDK 10.0.400, Aspire hosting packages 13.6.4, and OrbStack. The dashboard executable came from the locally installed Aspire 13.5.1 bundle.

| Median of three trials | Native F# | DSL |
| --- | ---: | ---: |
| Dashboard HTTP ready | 3.023 s | 3.069 s |
| Redis, API, and frontend ready | 8.306 s | 8.288 s |

Both modes had similar startup times in this run. The resource-readiness ranges overlapped, and three trials per mode give only a local baseline.

Earlier trials were discarded after the CLI selected Debug despite the Release argument and Redis cleanup overlapped successive launches. The recorded trials use explicit Debug output, wait for Redis shutdown, and use separate HTTP ports for the two services.
